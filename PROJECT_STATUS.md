Goal is learning + interview material, not just a working app: prioritize code Eric can explain, industry-standard patterns, and honest trade-off discussion over silently picking the "clever" option.

## Confirmed architecture decisions (do not relitigate without a real reason)

- **Stack:** Next.js (App Router) + TypeScript + Tailwind + Prisma + PostgreSQL (Neon), deployed on Vercel.
- **Scheduling engine is built in-house**, not a third-party API (Calendly/Acuity/Square) — this is the intended centerpiece interview story.
- **Double-booking prevention:** a fixed 15-minute slot table (`AppointmentSlot`) with a plain `@@unique([artistId, slotStart])` constraint, chosen deliberately over a Postgres exclusion/GIST constraint.
- **Payments (Stripe) deferred to v1.5**, after core booking flow works.
- **Mobile-first is a hard v1 requirement**, including a PWA shipping in v1. A native app (React Native/Expo) is explicitly deferred to a later phase — second frontend on the same API when it happens, no rewrite of booking logic.
- **AI receptionist (Twilio + Claude API) is explicitly out of scope** — design/roadmap only, do not implement without Eric explicitly reopening that scope.
- **Prisma uses `provider = "prisma-client"`** (newer client architecture), requiring an explicit driver adapter (`@prisma/adapter-pg`) — `PrismaClient` must always be constructed with `{ adapter }`.
- **Seed scripts must be idempotent** (`upsert` with fixed hardcoded seed IDs).
- **No timezone library in use anywhere** (no `date-fns-tz`/`Temporal`) — every local-time date operation assumes the server's local clock equals the salon's local clock. This is a deliberate, flagged simplification, not an oversight. Revisit if the deploy region ever differs from the salon's timezone, or the business expands to a second location.

## Completed so far

### Data layer
- Full schema migrated to Neon: `User`, `Artist`, `PortfolioImage`, `Service`, `Availability`, `TimeOff`, `Appointment`, `AppointmentSlot` (originally shipped with a typo — `AppointmenSlot` — renamed via a proper migration; confirmed safe since the table was empty at rename time).
- `AppointmentSlot_appointmentId_fkey` (and `_artistId_fkey`) are `ON DELETE RESTRICT` — anything deleting an `Appointment` must delete its `AppointmentSlot` rows first, in the same transaction.
- Seed script (`prisma/seed.ts`) is idempotent, seeds one artist, one service, one availability window. **Run it via `npx prisma db seed`, not `npx tsx prisma/seed.ts` directly** — the latter skips the `dotenv` load in `prisma.config.ts` and fails with `ECONNREFUSED`.
- `src/lib/prisma.ts` — shared `PrismaClient` singleton via the `globalThis` hot-reload-safe pattern, constructed with the `PrismaPg` adapter. All Prisma usage should import from here.
- `src/lib/availability.ts` — `getOpenSlots(artistId, date)`, the core availability engine: recurring `Availability` template for that day-of-week, minus `TimeOff` ranges for that date, minus already-booked `AppointmentSlot` rows. Verified against seed data (32 open slots on a clean Tuesday, correctly drops when time-off/bookings are added).

### API routes (all verified against the live database, not just typechecked)
- `POST /api/appointments` — booking creation, requires a session (`requireUser()`; books as the session's user, not a client-supplied id — see "Both known auth gaps closed" below). Validates input, checks grid-alignment (must land on a 15-minute boundary) and that the time isn't in the past, confirms artist/service exist and the request against `getOpenSlots` before attempting a write, then creates the `Appointment` + all `AppointmentSlot` rows in a single `prisma.$transaction` (required because `AppointmentSlot.appointmentId` isn't known until the `Appointment` insert returns its generated id). Catches `P2002` (unique constraint race) and returns `409` instead of a raw crash.
- `GET /api/services` — list all services.
- `GET /api/artists` — list all artists.
- `GET /api/artists/:id/availability?date=` — thin wrapper around `getOpenSlots`. `date` is parsed as `"YYYY-MM-DD"` via the multi-arg `Date` constructor (not `new Date(dateString)`, which parses bare date strings as UTC and can land on the wrong calendar day once shifted to local time) — with round-trip validation to catch out-of-range values (month 13, day 45, etc.).
- `GET /api/appointments/me` — lists the session's own appointments (`requireUser()`; no more client-supplied `userId` query param), full history, no status filtering yet.
- `DELETE /api/appointments/:id` — cancels a booking, requires a session (`requireUser()`) and ownership of the appointment (`403` if it belongs to someone else). **Soft-cancel, not a hard delete** (see below) — deletes the `AppointmentSlot` rows (freeing the slot grid) and sets `Appointment.status` to `CANCELLED` in one transaction, keeping the `Appointment` row itself. Returns `404` for an unknown id.

- **Appointment cancellation is a soft status update, not a real deletion**, as of this session — decided explicitly (not defaulted) after noticing `Appointment.status` already had a `CANCELLED` value that only makes sense under soft-cancel semantics, the same reasoning behind `Service.active`. Both `DELETE /api/appointments/:id` (customer-facing, retrofitted) and `PATCH /api/admin/appointments/:id` with `status: "CANCELLED"` now do the same thing: delete the appointment's `AppointmentSlot` rows (so the slot grid opens back up for rebooking — the historical `Appointment` row alone doesn't block `getOpenSlots`, only its slots do) and set `status: "CANCELLED"`, in one transaction. The `Appointment` row itself is kept. Verified live end-to-end, including a direct DB check: a cancelled appointment's slot count actually drops to `0` while its row and `status` persist, and the freed time reappears in `GET /api/artists/:id/availability`.

### Both known auth gaps closed
- **`POST /api/appointments`, `GET /api/appointments/me`, and `DELETE /api/appointments/:id` all now derive identity from the session instead of trusting client input.** Added `src/lib/require-user.ts` — `requireUser()`, same Response-to-short-circuit shape as `requireAdmin()`, but returns the session's user id on success (`Promise<Response | string>`) since these routes need the id itself, not just a pass/fail gate. `POST` no longer reads `userId` from the body at all (removed, rather than accepted-but-ignored, so there's no confusing dead field in the request shape); `GET /me` no longer takes a `userId` query param. `DELETE` additionally got a real **ownership check** — `requireUser()` alone only proves *someone* is signed in, not that they own the appointment being cancelled, so it separately compares `appointment.userId` against the session id and returns `403` on mismatch (`404` is still used for "doesn't exist," matching this project's existence-check convention; `403` here means "exists, but not yours").

All verified live: `401`/`403` auth gate, unknown-artist `404`, invalid-date `400`, ungrid-aligned-time `400`, `startTime >= endTime` `400`, happy-path `201`, and five overlap cases (partial overlap, full containment, back-to-back adjacency correctly allowed, same-day gap correctly allowed, identical time range on a *different* day correctly allowed).
   - **`PATCH`/`DELETE` had a rough first draft with six real bugs, all found and fixed before verification** (not caught by `tsc` alone — several were logic bugs, not type errors): (1) the artist-existence check ran unconditionally even when `artistId` was omitted from the body, so any partial update that didn't touch `artistId` would call `prisma.artist.findUnique({ where: { id: undefined } })` and crash instead of skipping the check — fixed by gating it behind `artistId !== undefined`, matching `admin/availability`'s optional-field convention. (2) The date-derived `year`/`month`/`day`/`parsedDate` were declared inside `if (date !== undefined) { ... }` but referenced afterward in the overlap-query construction — out of scope, a hard compile error — fixed by hoisting `parsedDate` and computing an `effectiveDate` (`parsedDate` if provided, else the existing row's `date`) for anything downstream. (3) The overlap query didn't exclude the row being updated, so any PATCH — including a genuine no-op — would find itself in its own query results and get rejected as "overlapping itself," the identical bug class already hit once in `admin/availability`'s `PATCH`; fixed with `id: { not: timeOff.id }`. (4) The overlap comparison used the raw, possibly-`undefined` `startTime`/`endTime` from the request body instead of the already-computed `start`/`end` merged-with-fallback values — fixed to compare `start`/`end` consistently. (5) The final block called `prisma.timeOff.create(...)` instead of `.update(...)` — a leftover copy-paste from the `POST` handler — and additionally redeclared `const timeOff`, shadowing the row already fetched at the top of the function (a duplicate-identifier compile error). Fixed to build a partial `data` object from only the fields present in the body and call `prisma.timeOff.update({ where: { id: timeOff.id }, data })`, wrapped in the same `P2025`-race `try`/`catch` as `admin/availability`'s `PATCH`, returning `200` (not `201`) with `{ data: updatedTimeOff }`. (6) `DELETE` had `Response.json({ data: deleted, status: 200 })` — `status` in the body instead of the second `init` argument — the exact same mistake already found and fixed once before in `admin/availability`'s `DELETE`; only "worked" by coincidence since `200` is the default. Fixed to `Response.json({ data: deleted }, { status: 200 })`. All verified live against a running server with a second, disposable test artist to exercise cross-artist scenarios: 10 `PATCH` cases (`401`/`403`, unknown-id `404`, no-op self-PATCH correctly *not* flagged as self-overlapping, partial update omitting `artistId` entirely correctly succeeding instead of crashing, invalid time `400`, merged-value ordering check `400`, nonexistent-`artistId`-in-body `404`, a genuine overlap correctly rejected, and retargeting a row to a different, conflict-free artist correctly succeeding) and 5 `DELETE` cases (`401`/`403`, unknown-id `404`, a real delete returning the corrected response shape, and a second delete of the same id correctly `404`ing) — then confirmed directly via a DB query (not just the API's response) that the `PATCH` changes had actually persisted and the deleted row was genuinely gone.
   - **`admin/appointments` done — `GET` (list/filter) at `src/app/api/admin/appointments/route.ts`, `PATCH` (status transitions) at `src/app/api/admin/appointments/[id]/route.ts`.** Different shape from the last three resources: manages `Appointment` rows with real relations (`user`/`artist`/`service`) and owned `AppointmentSlot` rows, rather than a simple validated-fields row.
   - **`GET` had a rough first draft with real bugs**, found before adding the planned filters: `artistId` was wrongly required (`400` if missing), which defeats the point of an admin-wide view across all artists; a `startDate` param was read from the query string but never actually applied to the query (dead code); and the param name (`"Start"`, capitalized) didn't match this project's lowercase query-param convention (`date`, `userId`, etc.). Rewrote as a `where`-object builder with three independent optional filters: `artistId` (existence-checked, `404` if unknown — filters shouldn't silently return an empty list for a typo'd id), `status` (validated against the four `AppointmentStatus` enum values), and a `startDate`/`endDate` range (each independently optional, same round-trip local-date parsing pattern as `admin/time-off`, factored into a small local `parseLocalDate` helper since it's needed twice in this file). Verified live with two real booked appointments across two dates/statuses: 16 cases covering the auth gate, each filter individually (valid/invalid/unknown), the date range in both single-bound and combined forms plus `startDate > endDate` rejection, and all three filters combined together.
   - **`PATCH` is status-only by design** — `PENDING`/`CONFIRMED`/`CANCELLED`/`COMPLETED`, not open editing of `artistId`/`serviceId`/`startTime`. Changing the booked time would desync the `AppointmentSlot` rows already tied to the original `slotStart`; that's a "reschedule" feature (delete-old-slots-create-new-slots in a transaction, same shape as the booking transaction in `POST /api/appointments`) deliberately deferred rather than folded in here. Setting `status: "CANCELLED"` triggers the same slot-freeing transaction described above under "Appointment cancellation." Verified live: `401`/`403` auth gate, unknown-id `404`, invalid/missing `status` `400`, a `PENDING → CONFIRMED → COMPLETED` walk, and a `PENDING → CANCELLED` transition confirmed (via a direct DB query, not just the API response) to zero out the appointment's slot rows while keeping the row and its new status.

## Working style to continue

- Explain *why*, not just what to type — this is explicitly for interview prep.
- Verify claims against real behavior (run the code, hit the route, check the database) rather than asserting from reading the code alone — several real bugs in this project were only caught this way (missing `await`s that silently serialized to `{}}` or leaked Prisma internals, a `RESTRICT` foreign-key that made the delete route non-functional, a UTC-vs-local date parsing bug).
- When multiple valid approaches exist, lay out the real trade-offs and recommend rather than picking silently.
- Flag known limitations honestly as they're introduced instead of presenting incomplete work as finished.
- Keep scope creep out — Stripe, native app, and AI receptionist are deliberately sequenced later.
