## Confirmed architecture decisions (do not relitigate without a real reason)

- **Stack:** Next.js (App Router) + TypeScript + Tailwind + Prisma + PostgreSQL (Neon), deployed on Vercel.
- **Scheduling engine is built in-house**, not a third-party API (Calendly/Acuity/Square) — this is the intended centerpiece interview story.
- **Double-booking prevention:** a fixed 15-minute slot table (`AppointmentSlot`) with a plain `@@unique([artistId, slotStart])` constraint, chosen deliberately over a Postgres exclusion/GIST constraint.
- **No payment integration planned.** Stripe (or any payment processor) is explicitly out of scope, not deferred — this is a reversal of an earlier "v1.5" plan. `Appointment` has no `depositPaid`-style field and none should be added.
- **Mobile-first is a hard v1 requirement**, including a PWA shipping in v1. A native app (React Native/Expo) is explicitly deferred to a later phase — second frontend on the same API when it happens, no rewrite of booking logic.
- **Admins can book appointments (one-off and standing) on behalf of any user, including brand-new walk-ins with no account.** Built this session — see "Admin-books-for-any-user" under Completed below for the full account.
- **Global self-booking toggle — done.** Backed by an `AppSettings` singleton-row table (`id` fixed at `1`), read by both `POST /api/appointments` and `POST /api/appointments/recurring` and enforced only for non-admin callers — an `ADMIN` caller always bypasses it. See "Global self-booking toggle" under Completed below for the full build/bug account.
- **Deploying to Cloudflare Workers, not Vercel.** Changed per client direction. **Flagged risk, not yet verified**: this project is on Next.js 16.2.11 (pre-release) with Turbopack as the default bundler (per `AGENTS.md`'s breaking-changes warning). As of this decision, Cloudflare's own docs recommend **vinext** (not the older OpenNext adapter) as the default way to run Next.js 16 App Router projects on Workers — OpenNext's Cloudflare adapter does not support Turbopack and has documented conflicts with Next 16's Proxy architecture (Node-only APIs like `async_hooks` breaking under the Workers Edge runtime). vinext claims Next 16 + App Router support but is new enough that it hasn't been battle-tested by this project or confirmed compatible with this exact Next/Turbopack combination. This project has no `proxy.ts`/`middleware.ts` (auth is done via in-route `requireAdmin()`/`requireUser()` calls, not proxy-based gating), which sidesteps the specific Proxy-architecture conflict described above — but the Turbopack-vs-adapter question still needs a real `vinext` (or equivalent) trial build before deploy work is considered de-risked. Do not assume it "just works" — run Cloudflare's own compatibility check against this exact project first.
- **AI receptionist (Twilio + Claude API) is explicitly out of scope** — design/roadmap only, do not implement without Eric explicitly reopening that scope.
- **Prisma uses `provider = "prisma-client"`** (newer client architecture), requiring an explicit driver adapter (`@prisma/adapter-pg`) — `PrismaClient` must always be constructed with `{ adapter }`.
- **Seed scripts must be idempotent** (`upsert` with fixed hardcoded seed IDs).
- **No timezone library in use anywhere** (no `date-fns-tz`/`Temporal`) — every local-time date operation assumes the server's local clock equals the salon's local clock. This is a deliberate, flagged simplification, not an oversight. Revisit if the deploy region ever differs from the salon's timezone, or the business expands to a second location.

- `src/lib/availability.ts` — `getOpenSlots(artistId, date)`, the core availability engine: recurring `Availability` template for that day-of-week, minus `TimeOff` ranges for that date, minus already-booked `AppointmentSlot` rows. Verified against seed data (32 open slots on a clean Tuesday, correctly drops when time-off/bookings are added).

### API routes (all verified against the live database, not just typechecked)
- `POST /api/appointments` — booking creation, requires a session (`requireUser()`; books as the session's user, not a client-supplied id — see "Both known auth gaps closed" below). Validates input, checks grid-alignment (must land on a 15-minute boundary) and that the time isn't in the past, confirms artist/service exist and the request against `getOpenSlots` before attempting a write, then creates the `Appointment` + all `AppointmentSlot` rows in a single `prisma.$transaction` (required because `AppointmentSlot.appointmentId` isn't known until the `Appointment` insert returns its generated id). Catches `P2002` (unique constraint race) and returns `409` instead of a raw crash.
- `GET /api/services` — list all services.
- `GET /api/artists` — list all artists.
- `GET /api/artists/:id/availability?date=` — thin wrapper around `getOpenSlots`. `date` is parsed as `"YYYY-MM-DD"` via the multi-arg `Date` constructor (not `new Date(dateString)`, which parses bare date strings as UTC and can land on the wrong calendar day once shifted to local time) — with round-trip validation to catch out-of-range values (month 13, day 45, etc.).
- `GET /api/appointments/me` — lists the session's own appointments (`requireUser()`; no more client-supplied `userId` query param), full history, no status filtering yet.
- `DELETE /api/appointments/:id` — cancels a booking, requires a session (`requireUser()`) and ownership of the appointment (`403` if it belongs to someone else). **Soft-cancel, not a hard delete** (see below) — deletes the `AppointmentSlot` rows (freeing the slot grid) and sets `Appointment.status` to `CANCELLED` in one transaction, keeping the `Appointment` row itself. Returns `404` for an unknown id.

### Both known auth gaps closed
- **`POST /api/appointments`, `GET /api/appointments/me`, and `DELETE /api/appointments/:id` all now derive identity from the session instead of trusting client input.** Added `src/lib/require-user.ts` — `requireUser()`, same Response-to-short-circuit shape as `requireAdmin()`, but returns the session's user id on success (`Promise<Response | string>`) since these routes need the id itself, not just a pass/fail gate. `POST` no longer reads `userId` from the body at all (removed, rather than accepted-but-ignored, so there's no confusing dead field in the request shape); `GET /me` no longer takes a `userId` query param. `DELETE` additionally got a real **ownership check** — `requireUser()` alone only proves *someone* is signed in, not that they own the appointment being cancelled, so it separately compares `appointment.userId` against the session id and returns `403` on mismatch (`404` is still used for "doesn't exist," matching this project's existence-check convention; `403` here means "exists, but not yours").

### ⚠️ Read this before doing any Playwright-based verification
The last session ended when a live-verification run **crashed the user's PC with an OOM error**. Likely cause: this project's verification workflow throughout the admin-dashboard build was `npm install --no-save playwright` → launch a headless Chromium → run a test script → `npm uninstall playwright`, repeated many times over (once or more per handler checked, across four admin pages — dozens of cycles total). Several of those test scripts threw an uncaught exception on a Playwright selector timeout (a real, recurring issue this session — ambiguous `text=` locators matching hidden elements, stale multi-run state, etc.) **before ever reaching their `await browser.close()` call**. A script that dies before closing its browser leaks the headless Chromium process — it keeps running, orphaned, consuming memory, and nothing in this workflow ever checked for or cleaned up orphaned processes between runs. Across dozens of cycles, several of which errored out, this most likely accumulated enough leaked Chromium processes to exhaust system memory.

Before resuming any Playwright-based verification:
1. Check `ps aux | grep -i chrom` (or Task Manager) for orphaned Chromium/node processes first, and kill any found, before starting new work.
2. Wrap verification scripts in `try { ... } finally { await browser.close() }` (or Node's `using`/explicit-resource-management if available) so a failed assertion or timeout can never leak the browser process — this project's scripts so far have **not** done this, which is the actual root cause to fix, not just a one-time cleanup.
3. Consider batching multiple checks into one longer-lived Playwright session (one `chromium.launch()`, several test scenarios run against it, one `browser.close()`) instead of the many separate install/launch/uninstall cycles used throughout this session — fewer cycles means fewer chances to leak.
4. This is a real, structural gap in how this project has been verifying frontend work, not a one-off fluke — worth actually fixing the pattern (e.g., a small reusable verification helper script that guarantees cleanup) rather than just being more careful by hand next time.

## Working style to continue

- Explain *why*, not just what to type — this is explicitly for interview prep.
- Verify claims against real behavior (run the code, hit the route, check the database) rather than asserting from reading the code alone — several real bugs in this project were only caught this way (missing `await`s that silently serialized to `{}}` or leaked Prisma internals, a `RESTRICT` foreign-key that made the delete route non-functional, a UTC-vs-local date parsing bug).
- When multiple valid approaches exist, lay out the real trade-offs and recommend rather than picking silently.
- Flag known limitations honestly as they're introduced instead of presenting incomplete work as finished.
- Keep scope creep out — Stripe, native app, and AI receptionist are deliberately sequenced later.
- **When verifying with a headless browser (Playwright), always guarantee cleanup.** Wrap test scripts in `try { ... } finally { await browser.close() }` so a failed assertion or selector timeout can never leak the browser process — an earlier session's repeated install/launch/uninstall cycles without this safety net very likely leaked orphaned Chromium processes across many verification runs and ultimately crashed the machine with an OOM error. Check `ps aux | grep -i chrom` for orphans before starting a new round of verification if there's any doubt.
