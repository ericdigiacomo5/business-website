## Confirmed architecture decisions (do not relitigate without a real reason)

- **Stack:** Next.js (App Router) + TypeScript + Tailwind + Prisma + PostgreSQL (Neon). Deploy target is Cloudflare Workers, not Vercel — see the Cloudflare bullet below for the full reasoning and open risk.
- **Scheduling engine is built in-house**, not a third-party API (Calendly/Acuity/Square) — this is the intended centerpiece interview story.
- **Double-booking prevention:** a fixed 15-minute slot table (`AppointmentSlot`) with a plain `@@unique([artistId, slotStart])` constraint, chosen deliberately over a Postgres exclusion/GIST constraint.
- **No payment integration planned.** Stripe (or any payment processor) is explicitly out of scope, not deferred — this is a reversal of an earlier "v1.5" plan. `Appointment` has no `depositPaid`-style field and none should be added.
- **Checkout is a record-keeping step, not a charge.** Payment is always taken on the salon's physical POS terminal, outside this app. "Checking out" an appointment means an admin marks it `COMPLETED` and records which payment method the POS used (`CASH`/`CARD`/`OTHER`) via `Appointment.paymentMethod` + `Appointment.checkedOutAt` — done this session, see "Checkout" under Completed below.
- **Transactional email is built** (password reset, first) — see "Email + password reset" under Completed below. Full design/research is written up in `PLAN_EMAIL_PASSWORD_RESET.md`; the resulting gap analysis that flagged this and other missing features lives in `FEATURE_GAPS.md`. Provider is **Resend, called via raw `fetch()`, not the SDK** — the SDK's own Cloudflare example needs the `nodejs_compat` flag, which isn't worth adding to a deploy path (Cloudflare Workers, see below) that already has an unresolved adapter question. Templates are plain HTML strings, not `react-email` (which has a documented Workers startup-CPU failure). With no `RESEND_API_KEY` set, `src/lib/email.ts` falls back to a console dev-driver — the whole feature is testable locally with zero setup and zero spend.
- **Mobile-first is a hard v1 requirement**, including a PWA shipping in v1. A native app (React Native/Expo) is explicitly deferred to a later phase — second frontend on the same API when it happens, no rewrite of booking logic.
- **Admins can book appointments (one-off and standing) on behalf of any user, including brand-new walk-ins with no account.** Built this session — see "Admin-books-for-any-user" under Completed below for the full account.
- **Global self-booking toggle — done.** Backed by an `AppSettings` singleton-row table (`id` fixed at `1`), read by both `POST /api/appointments` and `POST /api/appointments/recurring` and enforced only for non-admin callers — an `ADMIN` caller always bypasses it. See "Global self-booking toggle" under Completed below for the full build/bug account.
- **Deploying to Cloudflare Workers, not Vercel.** Changed per client direction. **Flagged risk, not yet verified**: this project is on Next.js 16.2.11 (pre-release) with Turbopack as the default bundler (per `AGENTS.md`'s breaking-changes warning). As of this decision, Cloudflare's own docs recommend **vinext** (not the older OpenNext adapter) as the default way to run Next.js 16 App Router projects on Workers — OpenNext's Cloudflare adapter does not support Turbopack and has documented conflicts with Next 16's Proxy architecture (Node-only APIs like `async_hooks` breaking under the Workers Edge runtime). vinext claims Next 16 + App Router support but is new enough that it hasn't been battle-tested by this project or confirmed compatible with this exact Next/Turbopack combination. This project has no `proxy.ts`/`middleware.ts` (auth is done via in-route `requireAdmin()`/`requireUser()` calls, not proxy-based gating), which sidesteps the specific Proxy-architecture conflict described above — but the Turbopack-vs-adapter question still needs a real `vinext` (or equivalent) trial build before deploy work is considered de-risked. Do not assume it "just works" — run Cloudflare's own compatibility check against this exact project first.
- **AI receptionist (Twilio + Claude API) is explicitly out of scope** — design/roadmap only, do not implement without Eric explicitly reopening that scope.
- **Prisma uses `provider = "prisma-client"`** (newer client architecture), requiring an explicit driver adapter (`@prisma/adapter-pg`) — `PrismaClient` must always be constructed with `{ adapter }`.
- **Seed scripts must be idempotent** (`upsert` with fixed hardcoded seed IDs).
- **No timezone library in use anywhere** (no `date-fns-tz`/`Temporal`) — every local-time date operation assumes the server's local clock equals the salon's local clock. This is a deliberate, flagged simplification, not an oversight. Revisit if the deploy region ever differs from the salon's timezone, or the business expands to a second location.

### API routes (all verified against the live database, not just typechecked)
- `POST /api/appointments` — booking creation, requires a session (`requireUser()`; books as the session's user, not a client-supplied id — see "Both known auth gaps closed" below). Validates input, checks grid-alignment (must land on a 15-minute boundary) and that the time isn't in the past, confirms artist/service exist and the request against `getOpenSlots` before attempting a write, then creates the `Appointment` + all `AppointmentSlot` rows in a single `prisma.$transaction` (required because `AppointmentSlot.appointmentId` isn't known until the `Appointment` insert returns its generated id). Catches `P2002` (unique constraint race) and returns `409` instead of a raw crash.
- `GET /api/services` — list all services.
- `GET /api/artists` — list all artists.
- `GET /api/artists/:id/availability?date=` — thin wrapper around `getOpenSlots`. `date` is parsed as `"YYYY-MM-DD"` via the multi-arg `Date` constructor (not `new Date(dateString)`, which parses bare date strings as UTC and can land on the wrong calendar day once shifted to local time) — with round-trip validation to catch out-of-range values (month 13, day 45, etc.).
- `GET /api/appointments/me` — lists the session's own appointments (`requireUser()`; no more client-supplied `userId` query param), full history, no status filtering yet.
- `DELETE /api/appointments/:id` — cancels a booking, requires a session (`requireUser()`) and ownership of the appointment (`403` if it belongs to someone else). **Soft-cancel, not a hard delete** (see below) — deletes the `AppointmentSlot` rows (freeing the slot grid) and sets `Appointment.status` to `CANCELLED` in one transaction, keeping the `Appointment` row itself. Returns `404` for an unknown id.

### Email + password reset — done
Built from a written plan (`PLAN_EMAIL_PASSWORD_RESET.md`), itself written in response to a gap analysis (`FEATURE_GAPS.md`) that flagged both as blockers: no password reset existed at all (permanent lockout for a forgotten password), and no email sending existed anywhere in the codebase.

**Email infrastructure** (`src/lib/email.ts`, `src/lib/email-templates.ts`): `sendEmail()` is a provider-agnostic wrapper — Resend via raw `fetch()` to their REST API when `RESEND_API_KEY` is set, a console dev-driver otherwise, and it never throws (a failed send shouldn't take down whatever triggered it). Templates are plain functions returning `{ subject, html, text }`, not `react-email` (documented Workers startup-CPU failure, and this project already has an unresolved Cloudflare adapter question — not worth a second unproven variable). `EMAIL_FROM`/`NEXT_PUBLIC_APP_URL`/`RESEND_API_KEY` added to `.env`.

**Password reset**: new `PasswordResetToken` model (deliberately separate from the existing unused `VerificationToken` table, which is Auth.js's own and only used by the Email/magic-link provider this project doesn't use) plus `User.passwordChangedAt`, both purely additive (migration `20260923233412_add_password_reset`, plain auto-diff, no hand-written migration needed). Tokens are 32 random bytes via Web Crypto (`crypto.getRandomValues`, not Node's `crypto` module — portable to the eventual Workers deploy), stored as a SHA-256 hash (never plaintext — same reasoning as `passwordHash`), 15-minute expiry, single-use.

`POST /api/auth/forgot-password` always returns an identical `200` body regardless of whether the account exists, has no password (a walk-in or Google-only account — sending either of those a reset link would be wrong, not just unnecessary), or already has a fresh unused token (a 60-second per-email cooldown, closing the free email-bombing-relay problem with no new dependency). The send itself runs via `after()` (`next/server`), unawaited, so response time can't leak whether an account exists — the timing side-channel the identical response text alone doesn't close. `POST /api/auth/reset-password` returns one identical error for "not found," "already used," and "expired," and does the password update + token-consumption + stale-token cleanup in a single transaction.

**The one real architectural gotcha, and the reason this took real thought rather than being a CRUD feature**: this project's session strategy is `"jwt"` (see the Auth section further down for why), which has no server-side session row to revoke — so by default, resetting a compromised password would do nothing to an attacker's already-active session. Fixed by adding `passwordChangedAt` to the `select` the `jwt` callback in `src/auth.ts` *already* runs on every request (the same mechanism that makes role changes and account deletion take effect immediately), and rejecting any token whose `iat` predates it. Cost: zero extra queries, since the read was already happening.

Extracted `PASSWORD_MIN_LENGTH`/`BCRYPT_COST` into `src/lib/password.ts` while touching this (`register/route.ts` now imports them too) — a third hand-copied pair would have been one too many, especially since `auth.ts`'s dummy-hash timing-safety trick depends on the cost factor actually staying in sync.

**Verified live** against the real dev database: unknown email, malformed email, and a real passwordless walk-in (`checkout-test-walkin@test.com`) all return the identical response with no token created; a real user's request logs the correct email via the dev driver; a second immediate request is silently cooled down (confirmed via dev-log line count, not just the response); a garbage token and a too-short password are both rejected correctly; and the critical test — sign in, reset the password via a second "device," re-check the first session — confirmed the first session's `/api/auth/session` goes from a live user object to `null` immediately after the reset, with no wait for expiry. Old password then correctly fails sign-in and the new one succeeds; reusing the already-used token is correctly rejected. UI verified via headless browser (Playwright, `--no-save`, `try/finally`-wrapped, fully uninstalled afterward): the "Forgot password?" link on `/login`, the `/forgot-password` confirmation state, the `/reset-password` no-token vs. with-token states, and the client-side mismatched-password check all work, zero console errors, correct styling at 375px matching the existing login/register forms.

### Admin past-time booking (Gap 3) — done, and fixed properly on a second pass
`FEATURE_GAPS.md` Gap 3 flagged that walk-in revenue was unrecordable: `POST /api/appointments` rejected any past `startTime` for everyone, admins included, so a walk-in served an hour ago could never be entered into the system. A first pass changed the route's own `isInPast` check to `(!isAdmin && isInPast)` — this was **necessary but not sufficient**, and shipped as if it were the complete fix.

**The gap the first pass missed**: `bookOccurrence()` (`src/lib/booking.ts`, shared by both booking routes) confirms real availability via `getOpenSlots()` (`src/lib/availability.ts`) before writing anything — and that function had its own, entirely separate `slot.getTime() < now` filter, with no `isAdmin` awareness at all. Relaxing the route-level check let an admin's request *past the outer gate*, but it then died one layer deeper with `"That time is not available"` — confirmed live: an admin POST for a genuinely free past slot returned `400`, not `201`.

**Fix**: `getOpenSlots(artistId, date, { allowPast? })` — an opt-in parameter, default `false`, so the public `GET /api/artists/:id/availability` route (which customers browse against, unauthenticated) and every other caller keep today's behavior with zero code changes. `bookOccurrence()` grew a matching `allowPast?: boolean` param threaded straight through, with a comment noting callers must derive it from the session's role themselves — the function has no way to verify that on its own. Both `POST /api/appointments` and `POST /api/appointments/recurring` now pass `allowPast: isAdmin` at their `bookOccurrence()` call sites (the recurring route's materialization loop calls this once per occurrence, so the fix applies uniformly across an entire backdated series, not just its first occurrence). The recurring route's own series-start gate (`firstOccurrenceStart.getTime() < Date.now()`) got the same `!isAdmin &&` treatment, since a backdated *standing* appointment (e.g. recording a recurring walk-in relationship that already started off-system) has the identical use case as a backdated one-off.

**Verified live**: the public availability route still hides past slots identically to before (unchanged for a date already partway elapsed). A non-admin's past-time booking attempt is still rejected — at the *outer* `400 "Time is invalid"` gate, confirming the non-admin path never even reaches the relaxed inner check. An admin's past-time booking on a genuinely open slot now succeeds (`201`), while an admin's past-time booking against a slot with a real conflict still correctly fails (proving `allowPast` bypasses only the time-in-the-past filter, not real double-booking prevention). A full backdated recurring series (3 weeks back, weekly) correctly materialized both of its past occurrences plus every future one, and correctly `skipped` (not silently swallowed) the one past occurrence that hit a genuine scheduling conflict from unrelated test data. All test appointments soft-cancelled afterward.

**Also found and fixed in passing, unrelated to this bug**: the dev-database seed admin's password no longer matched the documented `admin12345` default (a leftover `passwordChangedAt` stamp from a previous session's live verification of the password-reset feature, never restored) — reset back to the documented value. The global self-booking toggle was also found flipped to `false`; restored to the exact state found after testing, per instruction, rather than assumed back to the documented `true` default.

### Reschedule (Gap 4) — done, admin-only, time-only, same-artist
`FEATURE_GAPS.md` Gap 4 flagged that appointments could only be cancelled and rebooked, never moved — losing the original booking's identity and risking the slot being claimed in between. Scoped deliberately narrow before building, in a short back-and-forth: **admin-only** (at the time, the customer-facing case was entangled with Gap 5's then-fully-open cancellation-notice window — shipping customer self-service reschedule first would have let customers route around a policy that didn't exist yet; Gap 5 is now fully closed, see "Cancellation notice window (Gap 5)" below, so this deferral is worth revisiting rather than assumed to still apply as-is), **time only, same artist** (changing the artist or service is really "cancel and rebook" wearing a disguise, and was deliberately left out of v1 rather than folded in).

**API**: `PATCH /api/admin/appointments/[id]` — found genuinely broken mid-edit when this work started (a stray `import { start } from "repl"` and an incomplete `typeof startTime !== nu` line, not compiling). Rebuilt: `status` is now optional (a pure reschedule shouldn't have to restate the current status), and an optional `startTime` can be sent alongside it or alone — the route computes the *resulting* status (whichever wins if both are sent) to decide reschedule eligibility, so `status: "CANCELLED"` + a `startTime` in the same request is correctly rejected rather than silently doing something contradictory. The transaction frees the appointment's existing `AppointmentSlot` rows first (so a reschedule can land back on part of its own current time without a false conflict), re-validates the new time via `getOpenSlots(..., { allowPast: true })` — always `true` here since this whole route is already `requireAdmin()`-gated — and claims new slots; a genuine conflict throws inside the transaction and rolls back cleanly (verified live: a failed reschedule leaves the original slots completely intact, not half-deleted). `P2002` (a concurrent reschedule racing for the same slot) → `409`, matching `bookOccurrence()`'s own existing pattern.

**The `excludeAppointmentId` addition, and why it was needed**: `GET /api/artists/:id/availability` (which any date/time picker calls to show open slots) had no way to say "except this one appointment's own slots" — so the picker would show an appointment's *own current time* as unavailable, even though the PATCH route itself already frees those slots before checking the new time. Added `getOpenSlots(artistId, date, { excludeAppointmentId? })` and a matching query param on the route, **gated to admin callers only** (`auth()` checked, non-admin's param silently ignored — same pattern as the booking routes' `userId` override) since the route is otherwise public/unauthenticated and knowing an appointment id shouldn't let a stranger probe whether it currently holds a slot.

**Admin UI**: reuses the customer booking wizard's own `DateTimeStep` (day-strip + slot-grid) inside `ScheduleDetailSheet` — a `"Reschedule"` button sits between Confirm/Check Out and Cancel, swapping the action row for the picker (same pattern as the existing checkout flow's payment-method picker). `DateTimeStep` gained two new optional props (`excludeAppointmentId`, `heading`) that default to the booking wizard's existing behavior unchanged. **A real cross-cutting gap found while building this**: the schedule grid has no live refresh (`FEATURE_GAPS.md` Gap 16) and is scoped to a single day server-side, so rescheduling an appointment to a *different calendar day* would otherwise leave a stale block rendered at a nonsensical position on the original day until a manual reload. Fixed by passing the currently-displayed `date` down into `ScheduleGrid` as a new prop and comparing it against a reschedule's resulting `startTime`: same day → merge in place (sheet stays open), different day → remove from local state and close the sheet. Verified live both ways.

**Verified live**, every case: pure reschedule with no status change; combined confirm+reschedule in one request; rejection when rescheduling a `CANCELLED` appointment; rejection when status+startTime together would result in `CANCELLED`; off-grid/garbage/empty-body validation; conflict rejection with confirmed clean rollback; unauthenticated `401`/non-admin `403` (route-level, unchanged); past-time reschedule succeeding (admin latitude, same as Gap 3); a full regression pass confirming checkout and cancellation still work unaffected by the rewrite. Browser verification (Playwright, `--no-save`, `try/finally`-wrapped, uninstalled afterward): the Reschedule button, the picker rendering with the correct heading, an off-day reschedule correctly closing the sheet and removing the block from the original day's grid, and a same-day reschedule correctly showing the appointment's own current slot as pickable (confirming `excludeAppointmentId` actually works end-to-end, not just at the API level) while merging in place with the sheet staying open. All test appointments soft-cancelled afterward; booking toggle and admin password confirmed unchanged from their prior states.

### Cancellation notice window (Gap 5) — done
`DELETE /api/appointments/[id]` (the customer-facing cancel route) now rejects cancelling any appointment starting less than 24 hours out, closing the core "cancel five minutes before" case `FEATURE_GAPS.md` Gap 5 flagged. Started as Eric's own in-progress edit to this file, not built from scratch this session — the account below is honest about what was whose, across three passes: the buggy version found mid-edit, the notice-window fix, and closing the terminal-status gap that fix still left open.

**The version found mid-edit had a real, serious bug**: it called `requireAdmin()` — the shared short-circuit guard used everywhere else in this project, which returns `null` on success (admin) or a `Response` object on failure (non-admin), and returns early to short-circuit a route — and used its return value as a boolean (`!isAdmin`). Both cases are wrong to treat as a plain flag: `!null` is `true` and `!(a Response object)` is `false`, which is the **exact inverse** of what the variable name and its own comment ("admins have no such restriction") claimed. Traced with a full truth table across every `{admin/non-admin} × {status} × {within/outside 24h}` combination before touching anything, then confirmed live: with the buggy version, an admin could never cancel a `CONFIRMED` appointment through this route regardless of timing, while a customer cancelling their own `CONFIRMED` appointment *inside* the 24h window — the one case Gap 5 exists to stop — was never blocked at all.

**First fix attempt overcorrected**: replaced `requireAdmin()` with a direct `auth()` session read to get a real boolean, but kept an admin-exemption branch. **Corrected per Eric's direction**: this route only ever cancels the *caller's own* appointment (the ownership check just above it guarantees that — `appointment.userId !== userId` → `403`), so there's no scenario here where "admin acting on someone else's behalf" applies; that's what the separate `PATCH /api/admin/appointments/[id]` (no ownership restriction, no notice window) is for. Final version has no admin branch, no session read, no `isAdmin` at all — just `if (appointment.startTime < cancellationWindow)`, unconditionally, for whoever the (already-verified-to-be-the-owner) caller is.

**A side effect worth knowing**: this single `<` comparison also incidentally closes "cancel an appointment that already happened" from the original Gap 5 finding — a past `startTime` is always less than a 24-hours-in-the-future cutoff, so no separate past-time branch was needed.

**A gap the notice-window fix alone still left open, closed in a follow-up pass**: re-cancelling an appointment already in a terminal state (`CANCELLED`/`COMPLETED`) whose `startTime` is more than 24h out fell through the notice-window check (its `startTime` isn't "soon") and hit the cancel transaction again — not destructive (idempotent for `CANCELLED`, since its slots are already freed), but a real logic gap: the route would report `200` success for "cancelling" something that was already cancelled or already happened and got completed. Fixed with a status check ahead of the notice-window check — `if (appointment.status === "CANCELLED" || appointment.status === "COMPLETED")` → `400 "This appointment can no longer be cancelled"` — checked first since it's the more fundamental gate: timing is irrelevant to an appointment that can't be cancelled at all regardless of when it starts. **Not addressed, a separate and much smaller point**: the 24h figure is hardcoded, not a configurable `AppSettings` value (an option `FEATURE_GAPS.md`'s suggested-sequence section floated but wasn't required here).

**Verified live** against the real dev database, across both passes: a far-future active appointment cancels successfully (`200`, `CANCELLED`); a genuinely near-term one — built by temporarily adding an `Availability` window for right now, since the seed artist's only real weekly slot (Tuesdays) was never close enough to "within 24h" to test against directly — is correctly rejected with the notice-window error (`400`) and confirmed completely untouched afterward; the separate admin route still cancels that same near-term appointment with no restriction, confirming the two paths stay properly independent. For the terminal-status fix specifically: re-cancelling that same appointment once it was already `CANCELLED` is now correctly rejected with the *new* error (not the notice-window one) and confirmed to leave the row untouched; a separate appointment marked `COMPLETED` (admin-confirmed then admin-completed, scheduled far in the future to isolate the status check from the timing check) is also correctly rejected and confirmed untouched (`paymentMethod`/`checkedOutAt` intact); a near-term *active* (`UPCOMING`) appointment still correctly gets the notice-window error rather than the new status error, confirming the two checks fire independently and in the right order. All test state (the temporary availability window, every test appointment, the booking toggle) restored to what it was before.

### Salon-wide closures & date-range time off (Gap 6) — done
`FEATURE_GAPS.md` Gap 6 flagged that time off was strictly per-artist and per-single-day, so closing for a holiday meant one row per artist, and a multi-day closure multiplied that again. Eric's first idea was adding a list of artist ids to `TimeOff` instead of the single `artistId` it has — rejected before building anything, in favor of the approach below, for two reasons written up in full in `PLAN_SALON_CLOSURES.md`: a list has to be re-populated by hand every time staff changes (so a closure created today silently excludes anyone hired afterward), and it wouldn't have touched the date-range half of the finding at all.

**Schema**: `TimeOff.artistId` is now nullable (`null` = salon-wide — blocks every artist, present *and future*, with zero maintenance as staff changes) and a new nullable `TimeOff.endDate` makes `[date, endDate]` an inclusive multi-day range when set (`null` = single-day, today's behavior unchanged). Both purely additive (migration `20260925003700_add_salon_wide_and_ranged_time_off`, plain auto-diff, FK relaxed to `ON DELETE SET NULL`) — every existing row is already valid under the new shape with no data migration needed. Considered a separate `SalonClosure` model instead of widening `TimeOff` and rejected it: `getOpenSlots` would then need to query two tables and merge results on every single availability check, for a distinction that's really one axis of the same concept.

**`getOpenSlots`** (`src/lib/availability.ts`) — the only production read path against `TimeOff` outside the admin routes, so this is the query that actually closes the gap; everything downstream of it (the slot filter, dedup, sort) needed no changes at all, since it only ever sees rows already scoped to the right artist and day. The query now matches a row that applies to this artist either directly or salon-wide (`OR: [{ artistId }, { artistId: null }]`), combined with a date-range overlap check. Extracted the date-overlap logic into a new shared `timeOffDateRangeOverlap(rangeStart, rangeEnd)` helper (same file) rather than hand-writing it three times across `getOpenSlots` and both admin routes' overlap checks — this project's own history (the `admin/availability` overlap bug, found and fixed twice independently before being unified) is exactly the failure mode that duplication risks.

**API routes**: `POST /api/admin/time-off` — `artistId` is now optional (omitted/`null` = salon-wide), `endDate` is a new optional field (rejects `endDate < date`, mirroring the existing `startTime >= endTime` check). The overlap check needed real widening, not just a bigger query: creating a *salon-wide* row has to check against every existing row regardless of artist (dropping the artist filter entirely in that case), not just other salon-wide rows — a salon-wide closure landing on a day an individual artist already has personal time off is still a real overlap worth flagging. `PATCH /api/admin/time-off/[id]` — `artistId` and `endDate` both got the three-way `undefined`/`null`/value convention `admin/services`'s `PATCH` already established for `Service.description` (don't touch / clear it / set it), so a per-artist row can be converted to salon-wide (or back) and a single-day row can be extended into a range (or back) without a separate endpoint. `DELETE` needed no change at all — deleting a salon-wide or ranged row is identical to deleting today's.

**A real, non-obvious bug found and fixed while building the UI, worth remembering**: the "All Artists (Salon-Wide)" sentinel constant was first defined and exported from `artist-selector.tsx`, a `'use client'` file. Importing that same named export from the Server Component page (`admin/time-off/page.tsx`) silently did **not** give back the real string — `console.error`-debugging it live showed `SALON_WIDE_VALUE: [Function (anonymous)]` server-side, not the string, which made every `selectedArtistId === SALON_WIDE_VALUE` comparison false and caused the exact symptom this surfaced as: the create form posting the literal sentinel string as `artistId` instead of `null`, which the API correctly rejected with `404 "Artist not found"`. This wasn't a caching artifact — confirmed by restarting the dev server with a fully cleared `.next` cache and reproducing identically. Root cause: a Server Component importing a non-component named export from a Client Component module doesn't reliably cross the RSC boundary the way a plain shared value does. Fixed by moving the constant to a new plain module, `src/lib/time-off.ts`, that both the client selector and the server page import from — the general lesson (worth remembering for any future shared sentinel/constant that a Server Component needs to compare against something a Client Component also uses) is that anything shared across that specific boundary belongs in a plain non-`'use client'` module, never defined inside one.

**Admin UI**: `ArtistSelector` (shared with `admin/availability`, which must stay completely unaffected) gained an opt-in `allowSalonWide` prop, defaulting to `false`, that adds the sentinel option only where explicitly requested — `admin/availability`'s own usage needed zero changes. `admin/time-off/page.tsx` treats the sentinel as a real selection (not the "no artist chosen yet" case that triggers its existing first-artist redirect) and queries `where: { artistId: isSalonWide ? null : selectedArtistId }`. `TimeOffForm` gained an opt-in "Multi-day range" checkbox (unchecked by default, so the common single-day case needs zero extra clicks) that reveals a second date input when checked — available regardless of salon-wide vs. per-artist, since a single artist can have a real multi-day vacation too. `AdminTimeOffRow` shows a date range (`Nov 27 – Nov 30, 2026`) instead of a single date when `endDate` is present, and a "Salon-Wide" `Badge` when `artistId` is `null`, so a mixed list stays visually distinguishable at a glance.

**Verified live**, every case from the plan: a salon-wide closure blocks every artist's slots that day — including a brand-new artist created *after* the closure row already existed, confirmed by creating one live and checking their availability was already blocked with zero rows referencing them, which is the actual point of this whole design and the exact case a list-of-artist-ids couldn't have handled. A per-artist closure still only blocks that one artist (regression-checked against a second artist, unaffected). A 4-day range blocks every day in `[date, endDate]` inclusive and correctly leaves the day immediately before and after open — verified with real availability data across all 6 days, not just the boundary claims. The widened overlap check correctly rejects a new salon-wide row against an existing per-artist closure and vice versa (both directions tested). `PATCH` with `artistId: null` correctly converts an existing per-artist row to salon-wide (and a previously-open other artist is immediately blocked by it); `PATCH` with `artistId` omitted correctly leaves it untouched. `PATCH` extending then clearing `endDate` correctly widens then re-narrows the blocked range. All four cases (different-day, full-containment, non-overlapping-gap, back-to-back) verified live against a running server, not just reasoned through.

Reasoning: the dedup logic is reactive (cleans up bad data at read time) rather than preventing bad/confusing data from being written in the first place; the realistic mistake (an admin entering a *partially* overlapping window, e.g. an accidental lunch-break collision) wouldn't even be caught by exact-duplicate checking alone. Kept the existing `getOpenSlots` dedup in place regardless, as defense-in-depth against bad data arriving through some other path. ## Working style to continue

- Explain *why*, not just what to type — this is explicitly for interview prep.
- Verify claims against real behavior (run the code, hit the route, check the database) rather than asserting from reading the code alone — several real bugs in this project were only caught this way (missing `await`s that silently serialized to `{}}` or leaked Prisma internals, a `RESTRICT` foreign-key that made the delete route non-functional, a UTC-vs-local date parsing bug).
- When multiple valid approaches exist, lay out the real trade-offs and recommend rather than picking silently.
- Flag known limitations honestly as they're introduced instead of presenting incomplete work as finished.
- Keep scope creep out — Stripe, native app, and AI receptionist are deliberately sequenced later.
- **When verifying with a headless browser (Playwright), always guarantee cleanup.** Wrap test scripts in `try { ... } finally { await browser.close() }` so a failed assertion or selector timeout can never leak the browser process — an earlier session's repeated install/launch/uninstall cycles without this safety net very likely leaked orphaned Chromium processes across many verification runs and ultimately crashed the machine with an OOM error. Check `ps aux | grep -i chrom` for orphans before starting a new round of verification if there's any doubt.
