## What this project is

A nail salon booking platform for a real local salon ("Nail Image Inc.", Amityville, NY), built by Eric DiGiacomo (CS + Applied Math/Stats, Stony Brook, May 2026) as a portfolio/interview project. Priorities: code Eric can explain, industry-standard patterns, honest trade-offs over clever shortcuts.

**Stack:** Next.js 16.4.2 (App Router, Turbopack — read `node_modules/next/dist/docs/` before using an API, per `AGENTS.md`) · TypeScript · Tailwind v4 (CSS-only config) · Prisma 7.10.1 (`prisma-client` generator → `src/generated/prisma`, `@prisma/adapter-pg`) · PostgreSQL on Neon · Auth.js v5 beta (email and password only, JWT sessions, no database adapter) · Resend (raw `fetch`) · Cloudinary (signed browser uploads, served through `next/image`) · installable PWA. Deploy target: **Cloudflare Workers** (not done, see Roadmap).

## Architecture decisions (settled — don't relitigate without a real reason)

- **In-house scheduling engine** — the centerpiece interview story. No Calendly/Acuity/Square.
- **Double-booking prevention at the database:** fixed 15-minute `AppointmentSlot` rows with `@@unique([artistId, slotStart])`, chosen over a Postgres exclusion constraint. `P2002` → clean `409`. `AppointmentSlot` FKs are `RESTRICT`: delete an appointment's slots before the appointment, in one transaction. Every move of an existing appointment (admin reschedule/length/services, customer reschedule) goes through `reclaimSlots()` in `src/lib/booking.ts`.
- **No payments, ever.** Payment happens on the salon's POS. "Checkout" = admin marks `COMPLETED` + records `paymentMethod` (`CASH`/`CARD`/`GROUPON`/`OTHER`) + `checkedOutAt`. No `depositPaid`-style fields. `paymentMethod` is null only when nothing was left for the POS (store credit or a discount covered it).
- **Groupon is just a payment method.** Staff redeem the voucher in Groupon's Merchant Center; the app stores nothing about vouchers and does no verification (Eric's call, 2026-10-18 — overrides the voucher-tracking design in `PLAN_GIFT_CARDS_AND_VOUCHERS.md`).
- **Store credit is money the salon owes, kept as a ledger.** Append-only `CreditEntry` rows plus a cached `User.creditBalanceCents`, changed only through `addCredit()` / `spendCredit()` in `src/lib/credit.ts`, inside the caller's transaction. Debits are conditional updates (balance must cover it); `CHECK` constraints keep balances ≥ 0. Corrections are new entries (`ADJUSTMENT` with a reason, `REVERSED`), never edits. `npm run check-credit` reconciles cache vs ledger.
- **Artist pay data lives in its own tables** (`ArtistPayTerms`, `ServicePayTerms`, and the checkout snapshots `AppointmentPay` / `AppointmentServicePay`), never as columns on `Artist`/`Service`/`Appointment`/`AppointmentService`. Those rows reach customers through plain `include: { artist: true }` reads and `GET /api/artists` / `/api/services`, so a column there would publish everyone's pay. Only the admin artists/services pages (`ARTIST_PAY_TERMS_INCLUDE` / `SERVICE_PAY_TERMS_INCLUDE`), checkout and the pay report read them; all writes go through `src/lib/pay-terms.ts`. The commission rate (basis points) and each service's fee are **snapshotted at checkout**, so later changes never rewrite a past period. Setting a rate fills in (`backfilled`) visits checked out while the artist had none; fees are never applied retroactively (no snapshot = $0).
- **Gift cards are sold only as printed codes** and redeemed onto an account (whole value, once), where they become store credit. Codes: 16 chars / 80 bits from Web Crypto, stored only as SHA-256 (`src/lib/gift-card-code.ts`) — shown once at issue, for printing. Unknown / redeemed / void codes all get one identical error. No expiry, no fees (NY law).
- **Soft deletes for business records:** cancelling an appointment sets `status` and deletes only its slots; services and artists deactivate via `active`. Availability, time off, and portfolio images are hard-deleted (nothing references them).
- **Auth:** every route that needs identity calls `requireAdmin()` / `requireUser()` (or `auth()` when it needs the role) **inside the route** — no `proxy.ts`/middleware gating, per Next 16's own guidance. **Every admin page awaits `requireAdminPage()` (`src/lib/require-admin-page.ts`) as its first statement, before any query.** `admin/layout.tsx`'s check is UI only: Next renders a page in parallel with its layout, and before this rule pages streamed customer data to signed-out requests inside the layout's redirect (SECURITY_AUDIT C1, 2026-10-18). `src/lib/route-guards.test.ts` (`npm test`) enforces both rules. JWT strategy (database sessions were broken for Credentials); the `jwt` callback re-reads the user each request, so role changes, deleted accounts, password resets (`passwordChangedAt`), "sign out of all devices" (`sessionsRevokedAt`), email verification (`emailUnverified`) and profile completeness (`profileIncomplete`) take effect immediately. Sessions slide (8 h idle) but also have an **absolute** limit from sign-in (`authTime`): 12 h for admins, 14 days for customers. `SAFE_USER_SELECT` (`src/lib/user-select.ts`) is the only allowed way to read users that leave the server.
- **Email verification:** a self-registered account's address is unverified until its owner clicks the emailed link (`src/lib/email-verification.ts`, `POST /api/auth/verify-email` from a button on `/verify-email` — not a GET, so mail scanners can't use links up). Until then the customer can't self-book and gets **no booking emails** (`mayEmail()` in `appointment-emails.ts`). Changing one's own email needs the current password and only takes effect when a link sent to the new address is used; the old address is notified. A password reset also counts as verification. Staff-entered walk-ins (no password, can't sign in) are vouched for by staff.
- **Email and password is the only sign-in method.** Google sign-in was configured but never offered in the UI; it was removed on 2026-10-19 (Eric's call) rather than shipped untested, along with `@auth/prisma-adapter`. An account without a password is a walk-in. Customer names can't contain web or email addresses (`requiredPersonName()`), since names appear in emails.
- **CSRF is checked, not inherited:** `readJsonObject()` refuses any `Origin` that isn't the site's own (`403`) and any body not sent as `application/json` (`415`) — a `text/plain` form post can carry valid JSON, so parsing alone never stopped one. Mutating handlers without a body call `rejectCrossOrigin(request)`. The session cookie's `SameSite=Lax` is the second layer.
- **Emails are stored lowercased and trimmed** (`normalizeEmail()`), on every write and every lookup — registration, sign-in, password reset, profile and admin edits, the seed and the promote-admin script.
- **Images are Cloudinary-only.** The API accepts artist/portfolio image URLs only from the salon's own Cloudinary account (`isOwnCloudinaryUrl()`, which accepts nothing if `CLOUDINARY_CLOUD_NAME` is unset); there's no paste-a-URL field. That's what lets the CSP `img-src` and `images.remotePatterns` name one host. Display goes through `CloudinaryImage` (`src/components/ui/cloudinary-image.tsx`).
- **REST API + client `fetch()` for mutations, not Server Actions** — a future React Native app must reuse the same API. Server Components read with Prisma directly; Client Components call `/api/*`.
- **Admin overrides are derived from the session role, never the request body:** admins may book for any user (`userId`), at any length (`durationMinutes`), in the past, past the 14-day window, and while self-booking is closed. A non-admin's override fields are silently ignored.
- **Salon policies live in `AppSettings`** and are edited on `/admin/settings` (the Bookings page shows a notice linking there while online booking is closed): the self-booking on/off switch, `cancellationNoticeHours` (default 24 — the online cancel/reschedule window) and `maxSeriesWeeks` (default 52 — longest standing appointment). Read server-side with `getPolicySettings()` / `isBookingEnabled()` (`src/lib/settings.ts`); every customer-facing mention (About page, My Bookings, emails, error messages) reads the live value.
- **Email:** `sendEmail()` (`src/lib/email.ts`) never throws; with no `RESEND_API_KEY` it logs to the console instead of sending — **in development only**: a production build with no key sends nothing and logs no body (bodies contain live reset/verification links). Templates are plain strings that HTML-escape every interpolated value (no `react-email` — Workers startup-CPU issue). Sends run in `after()` so responses never wait on them.
- **PWA, kept deliberately small:** `src/app/manifest.ts`, icons in `public/icons/`, and a hand-written `public/sw.js` (no Workbox/next-pwa) that caches only content-hashed build assets plus a self-contained `public/offline.html`. **Pages and `/api/*` are never cached** — booking data must be live, and signed-in pages hold personal data. Registered in production builds only.
- **Rate limiting happens at Cloudflare's edge, not in the app** — rules are in the deploy runbook.
- **Mobile-first is a hard requirement** (375px first, 44px tap targets — the schedule grid's rows grow to 44px on touch screens). A native app is deferred.
- **Out of scope unless Eric reopens it:** payments, AI receptionist (Twilio + Claude), native app.
- **Timezone: the salon's clock, whatever the server's** (fixed 2026-10-22, no library).
  - `src/lib/salon-time.ts` holds `SALON_TIME_ZONE = "America/New_York"` and two `Intl` primitives, `zonedParts()` and `zonedToInstant()`.
  - The usual helpers are built on them: `startOfDay`, `startOfWeek`, `endOfDay`, `timeStringToDate`, `isOnSlotBoundary` (`schedule-grid.ts`); `toLocalDateKey`, `toLocalTimeKey`, `parseLocalDate` (`format.ts`); `addDays`, `generateOccurrenceDates` (`recurring.ts`). So are the display formatters `formatSalonDate` / `formatSalonTime` / `formatSalonDateTime`, used in the browser too.
  - A "date" is the instant of the salon's midnight.
  - **Only `salon-time.ts` may touch a Date's local fields or call `toLocale*String()`.** `salon-time-rules.test.ts` fails otherwise. `salon-time.test.ts` runs every check under five process time zones.
- **Texting (SMS) is opt-in, double opt-in, and per number** (built 2026-10-22, not yet live; guide in `docs/SMS_10DLC.md`).
  - The box on `/register` and My Account is never pre-checked and never required to book. Ticking it records consent for the profile phone (US numbers only, `toUsE164()`) and sends one "Reply YES" text. Appointment texts start only after the YES reply arrives through Twilio's webhook.
  - Every consent change goes through `src/lib/sms-consent-data.ts`, which writes an append-only `SmsConsentEvent` (proof of consent).
  - Staff can't opt anyone in. A phone change turns texts off. STOP keeps the number, so a later START turns texts back on.
  - Texts are sent from the email functions in `appointment-emails.ts`, via `appointment-sms.ts`, so every booking email has its text.
  - Reminders use their own claim column, `smsReminderSentAt`. Texts the app sends on its own go out only 8 AM–9 PM salon time.
  - Messages are GSM-7 only, one segment each (`sms-templates.ts`, tested).
  - `/api/sms/inbound` and `/api/sms/status` are Twilio webhooks checked by `X-Twilio-Signature`, not JSON/Origin. `route-guards.test.ts` checks the signature comes first.
  - With no `TWILIO_*` set, dev prints texts to the console and production sends nothing.
- **Seed scripts are idempotent** (`upsert` with fixed ids). Run `npx prisma db seed`, not `tsx prisma/seed.ts` directly (the latter skips `.env` loading). With nothing set it creates only `AppSettings`; demo rows and the default dev admin need `SEED_DEV_DATA=1` (refused under `NODE_ENV=production`). The first production admin comes from `npm run promote-admin`, which only promotes a verified email after a typed confirmation.
- **Customer booking caps** (`src/lib/booking-limits.ts`, enforced in both booking routes, admins exempt): at most 4 upcoming one-off bookings, 1 active standing appointment, and customer-created standing appointments of at most 12 weeks (or the salon's `maxSeriesWeeks` if shorter).
- **Which artist does which service** is `ArtistService` rows, and **no rows = every service** (so new services need no setup for those artists). Customers can't book an artist outside their list (both booking routes, `artistServicesError()`); admins may override and are warned. Rules: `src/lib/artist-services.ts` (pure) / `artist-services-data.ts` (writes).
- **Time off never silently overlaps bookings.** Both time-off routes save through `saveTimeOffChecked()` (`src/lib/time-off-conflicts.ts`): live, not-yet-ended bookings inside it → `409` + the list; re-sent with `cancelConflictingAppointmentIds` → they're cancelled and the time off saved in one transaction (conflicts re-found inside it), salon-worded emails in `after()`. Keep reads inside interactive transactions **flat** (no relation includes): Prisma reads relations with parallel queries on the one connection, which `pg` deprecates.
- **Server errors are reported, without a vendor SDK:** `src/instrumentation.ts` (`onRequestError`) and `reportError()` (`src/lib/report-error.ts`) write one JSON line per error (`"level":"error"`, no headers, no email addresses) and, with `ERROR_ALERT_WEBHOOK_URL`, post a throttled summary. Also `GET /api/health` and `CRON_HEARTBEAT_URL`. Runbook §11.

**Data rules worth knowing:**

- Appointment statuses: `PENDING → CONFIRMED → COMPLETED`, or `CANCELLED` / `NO_SHOW`. Cancelled and no-show free their slots and can't be reopened (a new booking is made instead). A customer reschedule puts the booking back to `PENDING` for staff to re-confirm.
- An appointment holds 1–8 services (`AppointmentService`) with **price and duration snapshotted at booking**. Its real length is `endTime − startTime` (`durationMinutesOf()`); the services give only the "usual" length.
- Discounts are per appointment (`discountType` + `discountValue`), set at checkout, and the total is derived (`src/lib/discount.ts`).
- Standing appointments (`RecurringAppointment`) book **every week up front** at creation (up to `maxSeriesWeeks`); weeks that can't be booked are saved as `RecurringSkippedOccurrence`. A series can only be cancelled as a whole; its individual appointments are edited like any other.
- Checkout order: services total → discount → store credit → what the POS charges (`amountDueCents()` in `src/lib/discount.ts`). Credit is applied only at checkout, never held on an open booking; `Appointment.creditAppliedCents` always equals minus its `SPENT` + `REVERSED` entries. "Return store credit" gives all of it back; to change the method afterwards, re-mark the visit `COMPLETED`.
- Pay report math (`src/lib/pay-report.ts`, pure and unit-tested): only `COMPLETED` visits, by `startTime`. "Sales" = services after the appointment's discount (store credit, gift cards and Groupon count at face value). The discount is spread over lines by price with largest-remainder rounding, so per-service rows add up exactly. Commission is rounded per visit. A visit with no rate makes commission and take-home "Unknown", never 0%.
- Customers can book up to 14 days ahead (`BOOKING_WINDOW_DAYS`, enforced server-side), within the per-customer caps above. Retired services and inactive artists can't be booked by anyone.
- Checkout is conditional on the appointment being unchanged since the request read it, so two simultaneous checkouts can't both spend credit (the second gets `409`).

**Emails sent:** booking confirmation, standing-appointment summary, cancellation (customer- vs salon-worded; salon-worded also when time off cancels a booking), reschedule (admin or customer), checkout receipt (with store-credit lines when used), standing-appointment cancelled, gift card added to account, password reset, email confirmation (signup / new address — no user-entered text in either), email-changed notice to the old address, and a 24h reminder via `POST /api/jobs/send-reminders` (`Authorization: Bearer $CRON_SECRET`). **Nothing calls the reminder job on a schedule yet.**

**Texts (to opted-in, confirmed customers):** booking confirmation, standing-appointment summary, reschedule, cancellation, standing appointment cancelled, and the 24h reminder (same job). Plus the opt-in "Reply YES" text. Not live until the migration is applied, the site is deployed and the 10DLC campaign is approved.

## Known limitations (accepted for now)

- Admin reschedule is time-only, same artist; customer reschedule is the same plus same length. Changing artist is cancel-and-rebook.
- A standing appointment just stops at its end date; nothing reminds anyone to renew it.
- Deleting a portfolio image or replacing a photo leaves the file in Cloudinary. One pre-uploads-only artist photo (`example.com`) in the dev database shows as initials until replaced.
- `npm audit` reports 5 "high" advisories, all in eslint-config-next's `braces`/`micromatch` chain — dev-only lint tooling; npm's only offered fix is a downgrade to Next 14.
- The portfolio manager's delete (×) button is 28px — admin-only, desktop-first, but under the 44px rule.
- Gift cards: the printed card carries the terms, as NY GBL § 396-i(3) requires, from the same `GIFT_CARD_TERMS` as the Terms page. Cards already printed keep their terms, and § 396-i forbids changing a card's terms after issue. An unredeemed card worth under $5 must be paid out in cash on request (the terms say so; cards can be sold from $1), and staff do that at the POS. A lost code can't be reprinted (only its hash is stored); the terms promise replacement only while it's unredeemed: void it and issue a new one. No "send by email" for e-gift cards. Customer redeem relies on the Cloudflare edge rate limit (runbook) plus 80-bit codes; there's no in-app attempt counter.
- Groupon: nothing stops staff from forgetting to redeem the voucher in Merchant Center; the app only records the method.
- Not yet asked of the client: their accountant's view on gift-card liability / NY unclaimed property (the gift cards page shows the total owed).
- Booking caps are count-then-book: two bookings sent at the same instant could both pass, so a determined account can exceed a cap by a booking or two (bounded by the edge rate limit).
- All admins are equally powerful and admin actions other than credit, gift cards and voids aren't logged (FEATURE_GAPS #21); design roles before artist logins (#12).

## Conventions

- **Route shape:** guard first (the first `await` — the test checks) → `readJsonObject(request)` (`src/lib/request.ts`; `403` cross-origin, `415` not JSON, `400` on bad JSON, non-objects and arrays), or `rejectCrossOrigin(request)` for a mutation with no body → validate with the helpers in `src/lib/validation.ts` (`normalizeEmail`, `requiredPersonName` for people's names, `requiredText`/`optionalText` with `TEXT_LIMITS`, `normalizePhone`), `isOwnCloudinaryUrl()` and `passwordError()` → existence checks return **`404`**.
- **Admin pages:** `await requireAdminPage("/admin/…")` as the first statement — never inside a `Promise.all` with queries. Responses are always `{ data }` / `{ error }`. `PATCH` fields are optional (`undefined` = don't touch, `null` = clear where allowed). Catch `P2025` → `404` and `P2002` → `409`.
- **Client-safe modules:** anything imported by a Client Component must not import Prisma, even transitively — this has broken the build three times. Pure helpers live in `salon-time.ts`, `sms-consent.ts`, `sms-templates.ts`, `twilio-signature.ts`, `schedule-grid.ts`, `format.ts`, `recurring.ts`, `appointment-services.ts`, `discount.ts`, `service-category.ts`, `validation.ts`, `time-off.ts`, `pay-report.ts`, `artist-services.ts`, `customer-summary.ts`, `calendar.ts` and `site.ts`; server-only logic lives in `availability.ts`, `booking.ts`, `settings.ts`, `appointment-emails.ts`, `appointment-sms.ts`, `sms.ts`, `sms-consent-data.ts`, `twilio-webhook.ts`, `pay-terms.ts`, `pay-report-data.ts`, `artist-services-data.ts`, `time-off-conflicts.ts`, `report-error.ts`, `salon-hours.ts`, `artist-cards.ts` and `exclude-appointment.ts`. The footer is a Server Component passed into the client `FooterGate` as `children` (a client module can't import it). Constants shared between a Server Component and a Client Component go in a plain module, never in a `'use client'` file. Server pages pass settings values down as props.
- **Migrations:** Prisma's auto-diff can't rename enum values, add a required column to a non-empty table, or add a unique constraint non-interactively. Hand-write those, name the folder with a **UTC** timestamp, apply with `prisma migrate deploy`, and **ask Eric first**. Each deploy so far has left Prisma's advisory lock held on Neon's pooled connection; release it with `SELECT pg_advisory_unlock(72707369)` (run it until `pg_locks` shows none).
- **Colors:** use the theme tokens in `globals.css` (`text-body`, `text-on-dark*`, `bg-cream`, `bg-band`, `text-lacquer`, `border-line`, `shadow-card`, …), not hex values in class names. ## Environment gotchas

- **Printing:** site chrome, admin nav and screen-only controls carry Tailwind's `print:hidden`. The gift-card print rule in `globals.css` is scoped with `body:has(.gift-card-print)` — unscoped, it blanked every other printed page.
- **Headless Chromium against `next dev` reloads in a loop** (seen 2026-10-18 on the login page: endless HMR "Compiled" + reload). Run browser verification against a production build (`next build && next start`) instead. Admin page `redirect()`s arrive as a 200 with a meta refresh (the `/admin/loading.tsx` boundary streams), so check them in a browser, not by expecting a 307.
- **Verification with a headless browser:** wrap scripts in `try/finally` so the browser always closes; check for orphan Chromium/node processes before and after; prefer one long Playwright session. Install Playwright in a scratch folder outside the repo rather than `--no-save` into it. Playwright's `setOffline` doesn't affect service-worker fetches — to test the offline page, stop the server. Leaked processes have crashed this machine once (OOM).
- **Only one `next dev` per project:** Next 16 refuses a second one ("Another next dev server is already running"). To test with different env vars, stop Eric's server first (ask), or use a production build (`next build && next start -p …`), which runs alongside it.
- **Dev server:** start test servers with `RESEND_API_KEY=""` (the `.env` has a real key — otherwise test bookings send real email). If a request hangs at "Compiling…", count `node` processes; a stale `.next` once spawned ~1,900. Kill them all, `rm -rf .next`, restart.
- **Production build locally** (`next build && next start`): needs `AUTH_URL` set or every sign-in fails with `UntrustedHost`. Dev output lives in `.next/dev`, so a production build doesn't disturb it. The service worker only runs in production builds.
- `next dev` may add or refresh a managed `<!-- BEGIN:nextjs-agent-rules -->` block in `AGENTS.md` (Next 16.3+); that's expected — commit it.
- npm now blocks package install scripts by default (`npm warn allow-scripts`). Prisma's engines were already present; if a fresh install breaks `prisma migrate`, run `npm approve-scripts prisma @prisma/engines`.
- Background processes started from the Bash tool are invisible to PowerShell's process tools — manage them from Bash (`netstat -ano`, `taskkill //PID`).
- App Router folders starting with `_` are private (not routed).
- JSX text that continues after `{…}` on a wrapped line can lose its leading space under Turbopack — build such sentences as one template string.
- `npm run promote-admin -- <email>` is the production way to create the first admin (interactive: it asks for the email again; the account must be verified). Procedure in runbook §3.
- A production build (`next build`) refuses to start without `CLOUDINARY_CLOUD_NAME` and `NEXT_PUBLIC_APP_URL` — both are read at build time.
- In dev, verification and reset links are printed to the dev server's console (`[email:dev] would send:`); in a production build with `RESEND_API_KEY=""` nothing is printed, so test those flows on `next dev`.
